## 記事の要約
- Agent Teamsは2026年2月5日にOpus 4.6と同時リリースされた実験的機能で、「Subagentsを拡張してステートフルにした機能」
- 各エージェントが `~/.claude/teams/` 配下のJSONファイルをポーリングし、メールボックスのアナロジーでメッセージングを実現している
- 実行モードはtmux（推奨・各エージェントが独立ペインで並列動作）とin-process（単一ターミナル）の2種類
- 実践例としてGitHub Issue解決にTeam「SOTA」を組織し、Explorer・Architect・Executorの3役割で協調作業を実施
- OSプロセスモデルに喩えると、AgentはシングルプロセスSubagentsはスレッド（親メモリ共有）、Agent TeamsはIPC協調の独立プロセス

## 詳細の深掘り

### Agent Teamsの内部アーキテクチャ

Agent Teamsの最も興味深い点は、そのメッセージング機構にある。各エージェントは独立プロセスとして動作し、`~/.claude/teams/` 配下のJSONファイルをインボックスとしてポーリングする。ファイルロックで排他制御しているため、推論エンジンとファイルシステムだけでメッセージングシステムが成立している。

この「ファイルシステムベースのIPC」は一見原始的だが、実装の単純さと堅牢性のバランスが取れた設計と言える。各エージェントが明確に分離されているため、1つのエージェントがクラッシュしても他に影響しにくい。

タスク管理も `~/.claude/tasks/チーム名/` 配下のJSONで行われ、依存関係（`blocks`/`blockedBy`）まで記録されている。

```json
{
  "id": "7",
  "subject": "実装: docker-cleanup.ts 作成",
  "owner": "executor",
  "status": "completed",
  "blocks": ["9"],
  "blockedBy": ["6"]
}
```

### 実践例：SOTAチーム構成と実際の動作

記事ではGitHub Issue #56（Docker内のnpm installボトルネック最適化）の解決にTeam「SOTA」を組織した実例が紹介されている。

チーム構成は以下の通り。

| メンバー | 役割 | 実際の活動 |
|---------|------|-----------|
| Explorer | コード調査 | 既存実装の発見・報告 |
| Architect | 設計 | 実装戦略・詳細計画書の作成 |
| Executor | 実装 | コードの実装・3つのcommitを達成 |
| Researcher | 調査 | 活動なし（役割不要と判断） |
| Setup | 環境構築 | 活動なし（役割不要と判断） |

注目すべきは、ResearcherとSetupが「活動なし」だった点である。エージェントが自律的に「自分の役割は不要」と判断してアイドル状態になったということであり、これはAgent Teamsの自律性を示している。

メモリ管理は `memory/` ディレクトリ下のファイルを共有する形式で、ArchitectがImplementation Planを書き、Executorがそれを参照して実装を進めるフローが自然に成立している。

### Subagentsとの使い分けとコスト意識

Agent TeamsとSubagentsの最も重要な違いは「コスト」と「自律性」のトレードオフにある。

- **Subagents**: 親エージェントからの単発タスク委譲。親のコンテキストをforkして軽量に動作する。大半のユースケースではこちらで十分
- **Agent Teams**: 各エージェントが独立したコンテキストを持ち、自律的に判断・協調する。複数インスタンス分のトークンを消費するため高コスト

トークン節約のため、記事では「プロンプトでSonnet/Haikuの使用を指示する」方法が推奨されている。全メンバーがOpusで動くとトークン消費が爆発的に増えるためである。

OSプロセスモデルの比喩が分かりやすい。Agentが単一プロセス、Subagentsがスレッド（親メモリを共有）、Agent Teamsはforkした独立プロセスがファイルシステム経由のIPCで協調する構成である。並列性と独立性は高いが、オーバーヘッドも大きい。

## キーポイント
- **ファイルシステムベースのIPC**: JSONファイルのポーリングとファイルロックだけでエージェント間メッセージングを実現しており、アーキテクチャが極めてシンプル
- **自律的な役割判断**: 不要な役割のエージェントが自動的にアイドル化するなど、チーム全体で効率的な自己組織化が起きる
- **コスト問題は深刻**: 複数のOpusインスタンスが並走するため、トークン消費は通常利用の数倍になる。Sonnet/Haikuへの切り替え指示が実質必須

## あなたへの関連性

### 実務への応用
Claude Code Skillsに強い関心があるなら、Agent Teamsは「大規模な作業を複数エージェントに分担させる」上位概念として押さえておく価値がある。ただし、現時点では実験的機能であり、コストも高いため、日常の個人開発では Subagents で十分なケースが大半と考えられる。

実用的なシナリオとしては、大規模なリファクタリング（調査→設計→実装の分業）や、複数リポジトリにまたがる変更作業が考えられる。

### 学習ヒント
Agent Teamsの内部実装（ファイルシステムIPC、タスクの依存関係管理）は、マルチエージェントシステムの設計パターンとして学びになる。特にJSONベースのタスク管理構造は、自分でClaude Code Skillsを設計する際の参考になる。

また、記事で紹介されているtmuxの活用はターミナルベースの開発効率向上に直結するため、tmux自体の基本操作を習得しておくとAgent Teams以外の場面でも役立つ。

## 議論の分析

### 主な論点
- Agent Teamsの実用性と現時点でのコストパフォーマンス
- マルチエージェントの「楽しさ」と実用価値の乖離

### 肯定的な意見
- ファイルシステムでIPCを実現する強引さが面白い
- タチコマ会議やマギシステムなど、SF的なマルチエージェント協調を連想させる

### 否定的な意見
- トークン消費（＝費用）が大きすぎるという懸念が複数
- 現時点では「わちゃわちゃ動いて楽しい」が主な価値で、実用面はまだ不明

### 補足情報
- 記事著者自身が「わちゃわちゃエージェントたちがパネル上で動いて楽しいのが現在の価値です（お金はかかります）」と率直に述べている
- 各エージェントのインボックスは `~/.claude/teams/` 配下のJSONで、実際のファイル構造を確認可能
