# 自分のコードをAIに攻撃させたら"守り"が全部ザルだった

> 元記事: [自分のコードをAIに攻撃させたら"守り"が全部ザルだった](https://zenn.dev/smartvain/articles/ai-attacked-my-code-security-mostly-placebo)
> 分析日: 2026-02-10
> ソース: はてブ
> ブックマーク数: 325 users

---

## 記事の要約
- 自律型AIハッキングツール「shannon」を使い、自身のWebアプリに対してセキュリティ診断を実施した体験記
- 15個のAPIエンドポイントのうち11個でIDOR（Insecure Direct Object Reference＝認可欠如）の脆弱性が発見された
- 主な脆弱性パターンはIDOR、Mass Assignment（リクエストボディをそのままDBに渡す）、情報漏洩（不要フィールドの露出）の3つ
- AIハッカーの最大の利点は「疲れない」こと。人間なら省略するマイナーなエンドポイントまで網羅的にチェックする
- 結論として「セキュリティはチェックリスト作業ではなく、自分のコードを悪意ある目で見つめ直す行為」であると主張

## 詳細の深掘り

### IDOR（認可欠如）の本質と、なぜ見落とされるのか

IDORはOWASP API Security Top 10で第1位に位置する脆弱性であり、「認証はあるが認可がない」という状態を指す。著者のコードでは以下のような実装になっていた。

```javascript
// 脆弱なコード: 認証済みユーザーなら誰のプロジェクトでもアクセスできる
const project = await prisma.project.findUnique({
  where: { id: params.id }
})
```

ログイン（認証）はしているが、そのリソースが「自分のもの」かどうかの検証（認可）が欠けている。この問題が厄介なのは、正常系のテストでは一切発覚しないという点にある。開発者は自分のアカウントでテストするため、自分のデータにアクセスできるのは「正常」に見えてしまう。

対策は `userId` 条件の追加と、認可ロジックのミドルウェア化である。

```javascript
// 修正後: オーナーシップを条件に追加
const project = await prisma.project.findUnique({
  where: {
    id: params.id,
    userId: session.user.id
  }
})
```

### Mass AssignmentとZodバリデーションによる防御

Mass Assignmentは、クライアントから送られたリクエストボディをバリデーションなしにそのままデータベースへ渡してしまう脆弱性である。これにより、本来ユーザーが変更できないはずのフィールド（例: `role`、`isAdmin`など）まで更新可能になる。

対策としてZodスキーマによる厳密なバリデーションが有効である。

```javascript
const UpdateSchema = z.object({
  name: z.string().max(100),
  description: z.string().max(1000).optional(),
})
const data = UpdateSchema.parse(await req.json())
```

さらに、APIレスポンス側でもDTO（Data Transfer Object）パターンを適用し、必要なフィールドだけを返却することで情報漏洩を防ぐ。

### 「防御者の思考」と「攻撃者の思考」の根本的な違い

記事の最も示唆に富む部分は、セキュリティにおける思考の非対称性への指摘である。

- **防御者の思考**: 「これを守ろう」 → 想定済みの攻撃に対して壁を作る
- **攻撃者の思考**: 「どこが甘い？」 → 想定外の穴を探し回る

著者はOWASPのチェックリストを上から順に潰していたが、チェックリスト自体が「防御者の思考」に基づいているため、実際の攻撃パターンとは乖離していた。AIハッキングツールは攻撃者の思考をシミュレートし、パラメータの組み合わせを変えながら網羅的に探索するため、人間が見落としがちな穴を発見できる。

## キーポイント
- **認証と認可は別物**: ログインできていることと、そのリソースへのアクセス権があることは全く別の問題である
- **AIの網羅性は人間を超える**: 人間のペンテスターは主要エンドポイントで妥協するが、AIは全エンドポイントのパラメータ組み合わせを延々と試行する
- **セキュリティの本質は「悪意の視点」**: チェックリストを暗記するより、自分のコードを攻撃者の目線で見つめ直す能力が重要

## あなたへの関連性

### 実務への応用
フロントエンドエンジニアとしてNext.jsやNuxt3でAPI Routes/Server Routesを実装する場面は多い。特にNext.jsのApp RouterではRoute Handlerを自前で書くことが多く、認可チェックの漏れは起こりやすい。記事で紹介されたミドルウェアパターン（`withOwnership`関数）は、Next.jsのRoute Handlerに直接適用できる実践的なパターンである。また、ZodによるリクエストバリデーションはNext.js/Nuxt3いずれにおいても標準的なアプローチとして導入しやすい。

個人開発でセキュリティ面のレビュアーがいない場合、shannonのようなAIツールを開発プロセスに組み込むことで、第三者視点のチェックを自動化できる可能性がある。

### 学習ヒント
セキュリティはフロントエンド開発者が見落としがちな分野だが、API設計に深く関わるため避けて通れない。OWASP API Security Top 10を一読しつつ、実際にAIツールで自分のコードを攻撃させてみることが最も効果的な学習方法になる。また、Zodバリデーションの習熟はTypeScriptの型安全性とも相性が良く、フロントエンド・バックエンド双方のスキル向上に直結する。

## 議論の分析

### 主な論点
- この脆弱性（IDOR）は基本的なものであり、そもそもセキュリティの基礎知識が足りていなかったのではないか
- AIツールによるセキュリティ診断の有用性と将来性
- 個人開発と企業開発におけるセキュリティレベルの違い

### 肯定的な意見
- AIに自分のサービスを攻撃させるという発想自体は、今後は公開前の最低ラインになるべき手法である
- 人間が飽きる全件チェックをAIが黙々とやってくれるのは実用的
- 自分の知識が浅い部分をAIに補強してもらう使い方として良いアプローチ
- 失敗を公開して知見を共有している姿勢は評価できる

### 否定的な意見
- IDORは「認証と認可の違い」というセキュリティの基本であり、AI以前の問題ではないか
- OWASPのチェックリストを上から潰したと言いつつ見落としているのは、知識だけで実践が伴っていない証拠
- 企業開発であればレビューやテストでも検出されるべきレベルの脆弱性

### 補足情報
- セキュリティ専門家のockeghem氏（徳丸浩氏）は「OWASP API Top 10ではBroken Object Level Authorization (BOLA)と呼ばれ、Top 1である。プロでもやりがちだ」とフォローしている

- 攻撃AIが手当たり次第にWebサービスを狙う将来のリスクを懸念する声もある
