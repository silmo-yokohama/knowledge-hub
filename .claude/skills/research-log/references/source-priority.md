# 取得手段の優先順位 + 引用ポリシー

`/research-log` のサブエージェントが情報を取得するときの厳守ルール。各 agent の prompt にこの方針を明示すること（agent が脊髄反射でヘッドレスブラウザを起動して時間と context を浪費するのを防ぐ）。

## 取得手段の優先順位（厳守）

「**まず探す → 対象に応じて最適な取り方を選ぶ**」の分岐型。常に直線的な順序ではなく、対象が何かによって 2 番目以降が分岐する。

### Phase 1: ディスカバリ（まず何を読むかを決める）

1. **`WebSearch`** — トピックから候補ソースを発見する。多くの調査は URL すら分からない状態でスタートするので、ここが起点
   - **例外**: ユーザーが具体的な URL を提示している、または公式 docs の URL が既知（`nextjs.org/docs` 等）の場合は Phase 1 をスキップして Phase 2 に直行してよい

### Phase 2: 取得（対象タイプに応じて分岐）

候補 URL / repo / 対象を見て、**対象タイプ別に最適な手段** を選ぶ:

2. **各種ターゲット専用 CLI / MCP** — 対象が以下なら最優先。構造化されていて速く正確、レート制限も扱ってくれる
   - GitHub（Issue / PR / Release Notes / repo content）→ `gh` または `mcp__github__*`
   - Supabase（logs / advisors / migrations）→ `mcp__claude_ai_Supabase__*`
   - Vercel（deployments / logs）→ `mcp__claude_ai_Vercel__*`
3. **`WebFetch`** — 上記の専用ツールが無い対象（公式 docs、ブログ、Qiita / Zenn / note 等の記事）。汎用 web 取得の標準
4. **`curl`** — `WebFetch` が空 / 404 / JS で空ページを返すケース、または API 直叩き / 認証ヘッダ要 / RSS・Atom feed 等の fallback
5. **ヘッドレスブラウザ**（`npx playwright` 等）— JS 実行必須の SPA で `curl` も空を返す場合のみ。1 件 5〜10 秒かかり遅いので最後の手段
6. **諦める** — ここまでで取れなければ「このソースは取得不能」とレポートに明示し、別ソースで代替する

### 原則

- **上位で取れたら下位は試さない**。下位に進むほど遅く / 重く / 脆くなる
- 対象タイプ判別が曖昧な時は `WebFetch` でいい（`gh` / MCP を無理にこじつけて使わない）

## 引用ポリシー

- **ソース URL は必ず付ける**。URL の無い「結果」は信用しない（LLM 幻覚の温床）
- **日本語以外の引用は「原文 + 日本語訳」をセット** で出す
  - 英語ソース → 原文 + 日本語訳
  - その他言語（中国語 / ドイツ語等）→ 原文 + 英訳 + 日本語訳（誤訳リスクを明示）
- 引用は **要点に限定**（長すぎる引用は要約に置き換え、引用範囲を明示）
- **複数ソースで裏取りできた事実** と **単一ソースの事実** を区別する（後者は「※ 単一ソース」と注記）
- **古い情報の警告**: 投稿日 / 最終更新が 2 年以上前なら「※ 古い情報、要再確認」と注記
- **URL は実在確認**: 怪しい URL は採用前に WebFetch で 200 が返るか確認する
