# /research-log - リサーチ蓄積スキル

あるトピックを **公式起点 → コミュニティ補完** で構造化 Web リサーチし、結果をチャットに提示したうえで **`01.Research/` にナレッジ資産として蓄積** する。蓄積されたレポートは後でブログネタ・学習素材として読み返せる。

グローバル `/research` の強化版。違いは2点:

1. **より深い調査**: サブエージェントを 3〜5 体に増やし、**反証検証（adversarial verify）** を挟んで主張の確度を上げる
2. **リポジトリ蓄積**: チャット出力で終わらせず、frontmatter 付き Markdown を `01.Research/` に保存する（将来 Astro 静的サイトで閲覧する前提のフォーマット）

## 設計思想

雑な検索は雑な答えを返す。良い調査は **情報源の階層** を意識する:

1. **公式 (一次情報)** — 仕様書 / 公式 docs / RFC / GitHub 公式 repo。「**何が正しいか**」の根拠
2. **コミュニティ (二次情報)** — Qiita / Zenn / はてブ / note / 個人ブログ / X / Reddit。「**どう使われているか / どこで詰まるか**」の補完

公式が薄い場合は二次情報に頼るが、その時は「個人の見解である」ことを明示する。公式が十分でも、コミュニティで「公式に書いてないハマりどころ / 実運用 tips」を必ず拾う。両方そろって初めて「使える調査結果」になる。

**蓄積物なので品質基準は高い**。チャットで流れて消える調査より一段深く・正確に。だから反証検証を必須にする。

## 手順

### Step 1. 調査トピックの分解と準備

1. ユーザーの依頼を読み、**調査軸 (sub-question) を 2〜4 個** に分解する。例「Next.js の Server Actions について」なら:
   - 軸1: 公式仕様（何ができる / API / 制約）
   - 軸2: ユースケース（どう使われているか）
   - 軸3: ハマりどころ・落とし穴
2. 分解した軸を 1 行ずつ提示し、不足が無いか確認する（短い依頼なら省略可、複雑なら必須）
3. Glob で `01.Research/*.md` を確認し（リサーチは 01.Research 直下にフラット配置。`viewer/` 配下は対象外）、**同一トピックの既存リサーチが無いか**チェックする
   - 既存があれば「追記・更新するか / 新規に作るか」をユーザーに確認する

トピックが巨大すぎる場合（「○○ 全体を調べて」）は、どの観点を優先するかを先に確認する。1 回で全網羅しようとしない。

### Step 2. 公式情報の調査（サブエージェント並列）

`Agent` ツールで **general-purpose** サブエージェントを起動。調査軸ごとに 1 体ずつ、**計 3〜5 体を並列起動**（同一メッセージで複数 Agent 呼び出し）。軸が少なければ 1 軸を複数観点に割って 3 体以上にする。

各 agent の prompt に明示すること:

- **調査対象**: トピックと該当する調査軸
- **取得手段の優先順位**: `references/source-priority.md` を厳守（まず WebSearch で発見 → 対象タイプ判別 → 専用 CLI/MCP（`gh` 等）が使えれば最優先 → 無ければ WebFetch → fallback で curl → 最後にヘッドレスブラウザ → 諦めて別ソース）
- **優先ソース順序**: ①公式 docs / 公式 GitHub repo ②RFC・標準化文書 ③提供元の公式ブログ
- **禁止**: この phase ではコミュニティソース（Qiita / Zenn 等）を参照しない
- **返却形式**: 各 finding に `{ 要点, ソース URL, 引用（原文＋必要なら訳） }` を付けて 400-600 words のレポート。冒頭に公式情報の充足度を **「十分 / 部分的 / 不足」** で自己評価

### Step 3. 充足度の判定

各 agent のレポートを読み、Claude 自身が **トピック全体** の充足度を判定する:

- **十分** → Step 4-A（補完調査のみ）
- **部分的** → Step 4-B（補完＋空白を埋める代替調査）
- **不足** → Step 4-C（二次情報メイン、ただし裏取り強化）

### Step 4. コミュニティ補完調査（サブエージェント並列）

公式を補強する **「公式に書いてない実運用知見」** を取りに行く。並列で:

- **対象ソース**: Qiita / Zenn / はてブ / note / 個人技術ブログ / X / Reddit
- **観点**: ユースケース（具体例）/ How to（手順・コード）/ 落とし穴 / 比較（該当時）
- **禁止**: 公式の単純な日本語訳記事は採用しない（情報量ゼロ）
- **返却形式**: Step 2 と同じ。各 finding にソース URL と引用必須

充足度に応じて:
- **4-B（部分的）**: 公式の空白箇所を agent に明示して埋めさせる
- **4-C（不足）**: 二次情報をメイン根拠に。**必ず複数ソースで裏取り**し、単一ソースは「※ 裏取り不能」と注記。発信者の信頼性（経歴 / Star 数 / 投稿日）もチェックし、結論の確度を下げて明示する

### Step 5. 反証検証（adversarial verify）★強化版の肝

ここがグローバル `/research` との最大の差。最終化の前に、**主要な主張（3〜5件）を別エージェントに反証させる**。

1. 各レポートから「重要だが鵜呑みにすると危険な主張」を 3〜5 件抽出する
2. 主張ごとに **検証エージェントを 1 体起動**し、次を指示:
   > 次の主張を **反証する** つもりで調べてください。誤り・例外・前提条件・バージョン依存・反例が無いか確認し、`refuted（誤り/要注意） / confirmed（裏取り成功） / uncertain` で判定してください。判断に迷う場合は uncertain にしてください。主張: 「○○」
3. 結果を統合:
   - **refuted** → サマリ/レポートから削除、または「要注意」として明示
   - **uncertain** → 「※ 確証なし」と注記して残す
   - **confirmed** → そのまま採用

検証は並列で起動してよい。トークン節約のため、検証対象は「効いてくる主張」に絞る（自明な事実は検証不要）。

### Step 6. クロスチェック

複数 agent のレポートと検証結果を読み、**矛盾している主張** を洗い出す:

- 矛盾あり → 「公式 A は X、ブログ B は Y」と両論併記
- 古い情報 → 投稿日 / 最終更新を確認。最新の公式と乖離していたら新しい方を優先
- URL は実在確認 → 怪しい URL は Claude 自身が WebFetch で 200 を確認してから採用（幻覚 URL 対策）

### Step 7. レポート生成（リポジトリ保存）

`references/report-template.md` のテンプレートに従い、**1 リサーチ = frontmatter 付き Markdown 1 ファイル**を保存する。

- **保存先**: `01.Research/YYYY-MM-DD_{slug}.md`
  - `{slug}` はトピックを短く表した **半角英数字＋ハイフン** のスラッグ（例: `nextjs-server-actions`）
  - 日本語トピックでも slug は英数字に変換する（Astro の URL / ファイル名安定のため）
  - 日付は実行日（`YYYY-MM-DD`）
- **frontmatter**: テンプレートのスキーマ（title / description / date / tags / category / sources / confidence）を埋める。**将来 Astro のコンテンツコレクションがこのスキーマを読む**ので、キー名と型を厳守する
- **本文**: 結論 → 調査結果（軸ごと・根拠 URL・引用）→ 注意点/矛盾 → 参照ソース一覧
- **図表**: 概念の関係・フロー・状態遷移などは **Mermaid** を埋め込む（クライアント描画でサイト側がレンダリングする前提。コードブロックは ```mermaid で記述）
- **言語**: レポート本文は日本語。英語引用は「原文＋日本語訳」をセットで

既存ファイルの上書きは禁止。同名ファイルがあればユーザーに確認する。

### Step 8. コミット & プッシュ & デプロイ（公開）

保存した Markdown を Git にコミットし、GitHub に push する。push が `main` に入ると GitHub Actions（`.github/workflows/deploy.yml`）が Astro サイトをビルドし、GitHub Pages に反映される。

1. 保存ファイルをステージしてコミット・push する:
   ```bash
   git add "01.Research/YYYY-MM-DD_{slug}.md"
   git commit -m "research: {タイトル}"
   git push
   ```
   - 既存リサーチを更新した場合も同様にコミットする
2. **現在のブランチが `main` の場合**は、デプロイの完了を待つ:
   ```bash
   gh run list --workflow=deploy.yml --limit=1   # 走り出した run を特定
   gh run watch <run-id> --exit-status            # 完了まで待機（1〜3分）
   ```
   - `gh` が無い / 認証されていない場合は、待機せず「反映まで 1〜2 分」と案内する
3. **`main` 以外のブランチの場合**は、push はするが「Pages は `main` 反映後にデプロイされる」と明示する（誤って「公開済み」と言わない）

ページURL（各リサーチ＝1ページ、slug から確定）:

```
https://silmo-yokohama.github.io/knowledge-hub/research/YYYY-MM-DD_{slug}/
```

### Step 9. チャットへのサマリ提示（公開URL付き）

保存・公開と合わせて、チャットにも要約を提示する（保存しただけで終わらせない）:

```markdown
# リサーチ結果: <トピック>

## 📌 結論 (TL;DR)
<3-5 行>

## 🔍 主な調査結果
- <軸ごとの要点>

## ⚠️ 注意点・矛盾・反証で覆った主張
- <あれば>

## 🌐 公開ページ
https://silmo-yokohama.github.io/knowledge-hub/research/YYYY-MM-DD_{slug}/

## 💾 保存先
01.Research/YYYY-MM-DD_{slug}.md
```

### Step 10. 完了報告

1. **公開ページURL**: `https://silmo-yokohama.github.io/knowledge-hub/research/YYYY-MM-DD_{slug}/`（デプロイ完了を確認できた場合はその旨、待機していない場合は「反映まで 1〜2 分」を添える）
2. **保存ファイル**: `01.Research/YYYY-MM-DD_{slug}.md`
3. **反証検証の結果サマリ**: confirmed / refuted / uncertain の件数
4. 必要なら「この内容をブログ下書き（/04.BlogDrafts）や学習ログ（/learning-log）の素材にできます」と一言案内（**自動では作らない**。橋渡しは手動）

## 注意・運用ルール

- **サブエージェント数の目安**: 公式 phase 3〜5 体 + コミュニティ phase 2〜4 体 + 検証 3〜5 体。トピック規模で調整し、無闇に増やさない（コンテキスト圧迫 + 統合コスト）
- **取得手段の優先順位は厳守**: `references/source-priority.md` 参照。上位で取れたら下位を試さない
- **agent への prompt は具体的に**: 「○○について調べて」ではなく「○○の△△について、公式 docs（URL）を起点に仕様・API・制約を 400-600 words で。各 finding にソース URL と引用を付与」のように対象 / 範囲 / 形式を絞る
- **引用の言語別ハンドリング**:
  - 日本語ソース → 引用そのまま、訳不要
  - 英語ソース → 原文＋日本語訳をセット
  - その他言語 → 原文＋英訳＋日本語訳（誤訳リスクを明示）
- **URL は必ず実在確認**: 幻覚 URL の混入を防ぐ
- **古い情報の警告**: 投稿日 / 最終更新が 2 年以上前なら「※ 古い情報、要再確認」と注記
- **調査範囲外**: 所属組織の内部情報 / 非公開情報 / 違法情報 / 特定個人のプロファイリングは扱わない（公開情報リサーチに限る）
- **公開前提の自覚**: 蓄積物は将来公開サイトに載る可能性がある。PII・私的な機密はレポートに含めない
- **メモリ保存（任意）**: 重要トピックは、ユーザーに確認のうえ memory（`reference` 型）にも要点を残してよい。デフォルトはリポジトリ保存のみ

## 例: 起動から終了までのフロー

```
User: "Astro のコンテンツコレクションについて調査して残して"

Step 1. 調査軸を3つに分解 → ユーザー確認
        既存 01.Research を確認（重複なし）
Step 2. Agent A/B/C 並列（公式 phase）→ 充足度 A:十分 B:部分的 C:不足
Step 3. 全体「部分的」と判定 → Step 4-B
Step 4-B. Agent D/E 並列（コミュニティ補完＋空白埋め）
Step 5. 反証検証: 主要主張4件を Agent F/G/H/I に反証依頼
        → 1件 refuted（古い API 仕様）→ 削除、1件 uncertain → 注記
Step 6. クロスチェック → 矛盾1件を両論併記
Step 7. 01.Research/2026-05-31_astro-content-collections.md を保存
Step 8. git add/commit/push → (main なら) gh run watch でデプロイ完了を待機
Step 9. チャットにサマリ提示（公開URL付き）
Step 10. 完了報告（公開URL + 保存先 + 検証結果 + 再利用案内）
```
